## 1. 文档目的与范围

### 1.1 文档目的

本文档定义「诗音」的产品目标、本期（阶段一）功能边界、数据模型、界面与交互规范、非功能要求与验收标准，作为架构设计、开发实现、测试验收的统一依据。本文自包含，阅读本文无需参考任何历史对话、代码或旧版本文档。

### 1.2 本期（阶段一）范围内

- 基于 React + TypeScript 的网页版音乐播放器，构建为纯静态站点；
- **导入用户本地音频文件并真实播放**（mp3 / m4a / wav / flac / ogg / opus），导入时解析内嵌标签（歌名 / 歌手 / 专辑 / 封面 / 歌词）；
- 音乐库浏览（歌曲 / 专辑 / 歌手 / 歌单四视图与排序）、搜索、收藏、播放历史；
- 播放体系：迷你播放条、全屏播放器、歌词页、显式播放队列、三种播放模式；
- 自建歌单（新建 / 改名 / 删除 / 加歌）、单曲操作菜单与单曲删除；
- 本地持久化：音频与元数据存 IndexedDB，收藏 / 历史 / 主题 / 歌单存 localStorage，刷新后自动恢复；
- 液态玻璃视觉语言（设计令牌 + 玻璃组件 + 封面取色氛围）；
- 设置页：主题切换、存储占用查看、清除全部本地音乐、关于；
- 发布到 GitHub Pages，可通过公网地址在手机 / 桌面浏览器访问；
- 全部功能在浏览器本地完成，不依赖自建服务端，不上传任何用户数据。

### 1.3 本期范围外（明确不做）

- 达到上架级质量标准的移动端与桌面端程序（阶段二 / 三，不实际发布）；
- 账号注册、登录、找回密码；
- 云收藏、云歌单、跨设备同步；
- 在线曲库、聚合音源、在线试听、在线下载、付费购买（版权与合规风险，产品定位明确排除）；
- 电台、直播、评论、社交点赞、一起听、动态分享；
- 推送通知；
- 任何内置示例曲目 / 示例歌单 / 模拟播放数据（产品只呈现用户自己导入的音乐）。

### 1.4 数据性质声明

产品**不内置任何曲目**：全部音乐来自用户在本机导入的音频文件，元数据（歌名 / 歌手 / 专辑 / 封面 / 歌词）优先取自文件内嵌标签，缺失字段才以文件名推断兜底。音频、封面与歌词只保存在用户设备的浏览器存储中，不上传服务器。曲库来源即用户自有文件，不存在第三方曲库授权问题（原 §11 Q-01 已关闭）。

## 2. 产品背景与定位

### 2.1 背景

诗音是一款去账号、去服务端的轻量音乐播放器，只播放用户自己的本地音乐。界面采用 React 生态实现，以统一设计语言与成熟组件构建精致的交互体验；长期以 Tauri 2 为跨平台框架，界面代码在网页、桌面、移动端复用，原生能力由 Rust 核心承担。产品按三阶段推进：网页版已作为真实可用的本地播放器交付，后续演进为达到上架级质量标准的手机 App 与桌面版。

### 2.2 产品定位

- **阶段一（本期，已交付）**：不联网、不登录的网页版本地播放器：导入本地音频真实播放，标签 / 封面 / 歌词解析，音乐库、自建歌单、播放队列与本地持久化齐备，已发布于 GitHub Pages 持续迭代（当前 0.7.0）。
- **阶段二**：手机 App 达到上架级质量标准（不实际发布），接入真实本地音频，由 Tauri Mobile 承载界面、Rust 核心提供音频与系统能力，存在明确成熟度与合规风险（见 §10.3）。
- **阶段三**：Windows 桌面版，接入真实本地音频，由 Tauri Desktop 构建安装包，复用同一套界面与 Rust 核心。

### 2.3 目标用户

| 用户类型 | 特征 | 核心诉求 |
| --- | --- | --- |
| 本地音乐用户 | 在手机 / 桌面浏览器播放自己导入的音乐 | 导入方便、整理清晰（库 / 歌单 / 队列）、数据只在本机、界面精致 |
| 后续开发者 | 基于现有网页版扩展多端（App / 桌面） | 结构清晰、模块边界明确、易扩展 |

### 2.4 设计原则

1. **本地优先**：不引入必须依赖服务端才能成立的功能。
2. **无虚构内容**：产品不内置示例曲目、不做模拟播放；界面呈现的一切都来自用户导入的真实文件，空状态如实引导导入。
3. **窄屏优先**：以手机竖屏视口为主要设计基准，桌面浏览器同时可用。
4. **克制依赖**：复用成熟组件，按需引入，不重复造轮子，不堆砌无关功能。
5. **统一语言**：颜色、字体、间距、圆角、图标、动画风格全局一致。
6. **分阶段诚实**：每阶段目标、能力边界、风险如实记录，不用后续阶段能力为当前阶段背书。

## 3. 产品路线（三阶段）

| 阶段 | 名称 | 目标 | 数据 | 发布 | 状态 |
| --- | --- | --- | --- | --- | --- |
| 阶段一 | 网页版 | 真实可用的本地播放器：导入播放、标签解析、音乐库 / 歌单 / 队列、本地持久化、液态玻璃视觉 | 用户导入的本地音频（IndexedDB / localStorage） | GitHub Pages | **已交付（0.6.1），持续迭代**：下一步 0.7 质感（深色模式 / 睡眠定时 / 歌词海报） |
| 阶段二 | 手机 App（上架级） | 达到上架级质量标准，复用网页版界面与逻辑 | 用户本地音频 | 不实际发布 | 否（后续，先做 Tauri 可行性调研） |
| 阶段三 | Windows 桌面版 | 构建桌面程序，复用同一套界面 | 用户本地音频 | 本地可安装程序 | 否（后续） |

### 3.1 阶段依赖关系

```
阶段一（网页，本期）
   │  复用界面组件与核心逻辑
   ▼
阶段二（手机 App，上架级）── 复用界面组件与 Rust 核心 ──► 阶段三（Windows 桌面）
```

- 三阶段共享同一套 React 组件与纯逻辑（切歌、歌词、搜索、主题）；
- 平台差异（音频、文件系统、原生能力）收口在 Tauri + Rust 核心层，不扩散到界面；
- 阶段二、三均为长期目标，其可行性受 Tauri 移动端成熟度与上架级合规要求约束，不在本期承诺。

## 5. 功能需求详述

### 5.1 底部导航（F-01）

**入口**：主界面底部常驻导航栏。

**需求**：

- 导航项固定为：主页、搜索、音乐库、我的，共 4 项（0.6 起原「发现」改为「音乐库」）；
- 形态为悬浮玻璃胶囊，当前项为玻璃药丸（白底高光 + 填充图标）；
- 点击某项后，对应主视图显示，其余主视图隐藏；当前项高亮；
- 导航状态在会话内保持，不随播放器覆盖层开合而重置；
- 每个导航项配有 Lucide 图标与文字标签，图标与标签垂直居中对齐。

**交互规则**：

| 操作 | 结果 |
| --- | --- |
| 点击导航项 | 切换当前视图，目标视图激活，图标与文字切换为强调色 |
| 再次点击当前项 | 状态不变，不重复刷新 |
| 键盘方向键 / Tab | 支持焦点在导航项间移动，回车激活 |

**状态反馈**：当前项以强调色 + 图标填充态标识；非当前项为中性灰。

### 5.2 曲目列表与点击播放（F-02）

**展示字段**：封面（内嵌封面图，无封面时渐变色块）、歌名、歌手 · 专辑、时长、收藏按钮、「…」操作菜单按钮。

**需求**：

- 主页展示全部曲目；音乐库按当前视图 / 排序展示；搜索结果展示全部命中曲目；
- 点击曲目行：将该曲设为当前曲目、进度归零、进入播放状态、打开全屏播放器，并写入最近播放；同时以所在列表的顺序重建播放队列（见 F-20）；
- 收藏与「…」按钮点击时不触发行的播放逻辑（阻止事件冒泡）；
- 曲目行在窄屏下：封面 48px 固定，中间信息区可截断，右侧时长与收藏按钮固定宽度。

**交互规则**：

| 操作 | 结果 |
| --- | --- |
| 点击曲目行 | 触发播放（见 §5.5 联动） |
| 点击收藏按钮 | 仅切换收藏态，不播放 |
| 当前正在播放的行 | 歌名以强调色显示，左侧显示播放中指示图标（动态音柱） |

**边界**：曲目集合为空时，列表区展示空态（见 §6.5）。

### 5.3 迷你播放条（F-03）

**需求**：

- 在主视图底部、导航栏上方常驻，高度 64px；
- 未播放时：标题显示「未播放」，副标题显示「选择一首歌开始」，播放按钮禁用态；
- 播放中或有进度时：展示当前曲目名、歌手、封面色块、播放/暂停按钮、进度条；
- 顶部有一条 2px 进度线，随播放进度填充；
- 点击条体打开全屏播放器；点击播放按钮仅切换播放/暂停，不打开播放器（阻止冒泡）。

**交互规则**：

| 操作 | 结果 |
| --- | --- |
| 点击条体（非按钮区） | 打开全屏播放器 |
| 点击播放/暂停按钮 | 仅切换播放状态，不打开播放器 |
| 长按封面色块 | 无动作（预留阶段二扩展） |

**状态反馈**：进度线以主题强调色填充；播放中封面色块轻微脉动（可选，遵循 §6.4 动效规范）。

### 5.4 全屏播放器（F-04）

**需求**：

- 由迷你播放条或曲目点击进入，覆盖全屏；可通过顶部返回按钮或下滑手势收起；
- 展示：封面唱片（播放中匀速旋转，暂停静止）、歌名、歌手 · 专辑、进度条与当前/总时长、控制按钮组；
- 控制按钮：播放模式切换、上一首、播放/暂停、下一首、收藏当前曲目；
- 右上角入口可打开歌词页；
- 封面唱片尺寸在窄屏约 72vw，桌面端限制最大宽度，保持居中。

**控制行为**：

| 控件 | 行为 |
| --- | --- |
| 上一首 | 切换到上一曲（环形取模），进度归零 |
| 下一首 | 切换到下一曲（环形取模），进度归零 |
| 播放 / 暂停 | 切换播放状态，唱片同步旋转 / 静止 |
| 模式切换 | 按 列表循环 → 单曲循环 → 随机播放 顺序轮换，图标随之切换 |
| 收藏 | 切换当前曲目收藏状态，图标填充 / 描边切换 |
| 返回 / 下滑 | 收起播放器，返回原主视图 |

**进度条**：支持点击跳转（点击位置换算为秒数），拖动时实时预览目标时间，松手后提交。

### 5.5 进度推进与自动切歌（F-05）

**需求**：

- 播放进度由真实音频引擎的 `timeupdate` 事件驱动（0.2 起替换原模拟计时，经平台适配层收口）；
- 音频自然结束（`ended`）时，按当前播放模式在**播放队列**内处理：
  - **列表循环**：切到队列下一曲（环形），进度归零；
  - **单曲循环**：进度归零，曲目不变；
  - **随机播放**：在队列内随机选取一首（优先排除当前曲），进度归零；
- 暂停状态下进度静止；
- 点击曲目播放、上一首、下一首均使进度归零并立即进入播放态。

### 5.6 搜索（F-06）

**需求**：

- 输入框输入关键词后，实时在本地曲目集合中过滤；
- 匹配范围：歌名、歌手、专辑（不区分大小写，包含匹配）；
- 关键词为空时展示全部曲目；
- 搜索结果复用曲目行组件，点击行为与 §5.2 一致；
- 输入框获得焦点时显示清除按钮，点击清空关键词。

**状态反馈**：无命中时展示空态提示（见 §6.5）。

### 5.7 收藏（F-07）

**需求**：

- 收藏集合保存曲目 id（整数）；
- 曲目行与播放器收藏按钮实时反映当前收藏态；
- 再次点击取消收藏；
- 「我的」页展示收藏数量并可点进收藏专页直接播放；
- 收藏持久化于 localStorage，刷新后自动恢复（0.3 起）。

### 5.8 歌词展示与跳转（F-08）

**需求**：

- 歌词页以列表展示当前曲目全部歌词行；
- 根据当前进度高亮应播放的歌词行；高亮规则：取时间戳不晚于当前进度的最后一行；
- 点击某行歌词，进度跳转到该行时间戳对应秒数；
- 切换曲目后，歌词列表与高亮随当前曲目刷新；
- 高亮行自动滚动至可视区中部（平滑滚动）。

**本期形态与演进**：歌词来自音频内嵌标签（LRC 同步歌词逐行高亮，带距离层级视觉；纯文本歌词整段展示不高亮）。逐字高亮不在当前路线内（候选方案许可为 AGPL，与 §8.6 冲突，已决策自研轻量歌词，不引入）。

### 5.9 播放模式（F-09）

| 模式 | 切歌策略 | 图标语义 |
| --- | --- | --- |
| 列表循环（List） | 顺序向下，末曲后回到首曲 | 循环箭头 |
| 单曲循环（Repeat） | 播放结束后重播本曲 | 单曲循环箭头 + 数字 1 |
| 随机播放（Shuffle） | 结束后随机选取曲目 | 交叉箭头 |

### 5.10 最近播放（F-10）

**需求**：

- 点击播放某曲时，将其索引加入历史记录；已在记录中则不重复插入，新记录置于最前；上限 100 条；
- 「我的」页展示历史记录条数并可点进最近播放专页；
- 历史持久化于 localStorage，刷新后自动恢复（0.3 起）。

- 切换后，全局 CSS 变量即时更新，界面配色随之变化，无需刷新；

### 5.13 GitHub Pages 发布与公网访问（F-13）

**需求**：

- 阶段一产物发布到 GitHub Pages，生成公网可访问地址；
- 手机浏览器、桌面浏览器均可访问主页并完成核心交互闭环；
- 发布地址写入交付说明，便于体验者直接打开。

**约束**：

- GitHub Pages 仅托管静态文件，本期网页产物为纯静态文件（HTML + JS + CSS），满足托管要求；

- 发布涉及远程仓库操作，属于对外发布行为，执行前须获得明确授权。

### 5.14 导入与内嵌标签解析（F-14 / F-16）

- 通过文件选择导入本地音频（mp3 / m4a / wav / flac / ogg / opus），按文件指纹（名 + 大小 + 修改时间）去重；
- 导入时以 music-metadata 解析内嵌标签：歌名 / 歌手 / 专辑 / 时长 / 封面图 / 歌词（LRC 同步歌词、同步歌词条目、纯文本歌词与非标准帧兜底）；逐字段以标签为准，缺失才回退文件名推断（「歌手 - 歌名」约定）；
- 解析失败不阻断导入，整体回退文件名方案；
- 导入结果写入 IndexedDB 持久化，启动时自动恢复并重建 blob URL。

### 5.15 音乐库（F-18）

- 「音乐库」Tab 顶部分段切换：歌曲 / 专辑 / 歌手 / 歌单；
- 歌曲视图可按导入时间、歌名、歌手排序（升 / 降序，中文排序规则）；
- 专辑 / 歌手按名称聚合，点进详情页（头图、播放全部、曲目列表）；聚合与排序保留曲目全局下标，播放行为与 §5.2 一致。

### 5.16 自建歌单（F-19）

- 歌单数据：名称 + 曲目 id 清单 + 创建时间，存 localStorage（序列化带清洗，损坏数据不致崩溃）；
- 支持新建、改名、删除（两段确认）、从歌单移除单曲、播放全部；
- 加歌入口在单曲操作菜单（F-21），含「新建并加入」。

### 5.17 播放队列（F-20）

- 播放顺序由显式队列（曲目下标的排列，不重复）决定：在某列表点播即以该列表顺序建队列；上一首 / 下一首 / 播完收尾均在队列内进行；
- 队列页（播放页入口）：拖拽手柄排序、移除非当前项、清空只保留当前、点按跳播；
- 单曲菜单提供「下一首播放」（移到当前之后）与「加入队列」（追加队尾）；
- 队列为会话态（不持久化），启动恢复后初始化为自然顺序；导入新曲目时按自然顺序追加队尾。

### 5.18 单曲操作菜单与删除（F-21）

- 曲目行尾「…」打开玻璃底部抽屉：下一首播放、加入队列、加入歌单、收藏 / 取消收藏、删除这首歌；
- 删除为真删除：IndexedDB 记录与 blob URL 一并处理；收藏按 id 剔除、历史与队列按下标重映射、歌单按 id 清理；删正在播的曲目则停播；菜单内红色二次确认，文案说明不影响设备上的原文件。

### 5.19 设置页（F-22）

- 入口在「我的」页；含主题配色（F-11）、数据管理与关于；
- 数据管理：显示本地音乐首数与存储占用估算；「清除全部本地音乐」二次确认后删除 IndexedDB 全部记录并重置相关状态（歌单保留空壳），不影响设备原文件；
- 关于：版本号与「数据只保存在本机」说明。

## 6. 界面与交互规范

本章定义全局设计语言与交互范式，所有界面实现须遵循。目标是视觉精致、语言统一、交互流畅，避免过度装饰。

### 6.1 设计语言

| 维度 | 规范 |
| --- | --- |
| 色彩 | 由主题 CSS 变量驱动：`--accent`（强调色）、`--bg`（背景色）、`--bg-end`（渐变收尾色）。中性文字与边框使用固定的灰阶令牌，不随主题变化。强调色仅用于高亮、选中、收藏、进度等语义位置。 |
| 字体 | 系统字体栈优先（无衬线），中文优先常见系统字体；不使用外部字体 CDN，避免加载失败。字号建立层级：标题 / 正文 / 辅助三级，行高统一。 |
| 间距 | 采用统一间距刻度（如 4 的倍数：4/8/12/16/24/32px），组件内边距与区块间距从刻度取值，不随意写死数值。 |
| 圆角 | 建立圆角令牌：小（按钮、标签）、中（卡片、输入框）、大（面板、播放器封面区），同类元素圆角一致。 |
| 图标 | 统一使用 Lucide 图标库，描边宽度、尺寸保持一致；同一语义在不同位置使用相同图标。 |
| 动画 | 统一使用 Motion 或 CSS 过渡：时长与缓动曲线建立令牌（快 150ms / 常规 250ms / 转场 350ms），全站一致；尊重系统「减少动态效果」偏好。 |

### 6.2 布局与响应式

- 移动端竖屏优先：主视图 + 底部导航 + 常驻迷你播放条，三段式垂直分区；
- 全屏播放器、歌词页为覆盖层，默认隐藏，激活时覆盖全屏；
- 断点：以窄屏（手机）、中屏（平板）、宽屏（桌面）三档适配；宽屏下内容区居中并限制最大宽度，避免元素过度拉伸；
- 视口设置 `width=device-width, initial-scale=1`，不禁止用户缩放；
- 长歌名、长歌手名需单行截断（省略号），避免撑破窄屏布局；
- 歌单卡片区支持横向滚动，滚动条按需隐藏。

### 6.3 双播放面设计

- 迷你播放条与全屏播放器共享同一份播放状态（当前曲目、进度、播放状态），切换页面或收起播放器均不中断进度推进；
- 从迷你条展开全屏播放器时，封面与标题使用共享元素过渡（layout 动画）放大至主视觉位置，收起时反向回落；
- 状态单一数据源：任一播放面的操作（播放 / 暂停 / 切歌 / 拖动进度）即时反映到另一面。

### 6.4 视觉细节

- 封面优先显示音频内嵌封面图，无封面时以渐变色块 + 播放符号呈现（色取曲目 `color` 字段）；播放页背景由封面取色生成光晕氛围（重度模糊封面 + 主色渐变），无封面时回退兜底色；
- 卡片使用令牌化圆角与浅色背景，克制阴影；
- 播放中封面唱片匀速旋转（CSS `transform` 动画，走合成器路径以保证流畅），暂停即停；
- 强调色用于高亮态、收藏态、选中态、进度填充；非激活元素使用中性灰，保证层级清晰。

### 6.5 交互反馈（加载 / 错误 / 空态）

| 状态 | 场景 | 表现 |
| --- | --- | --- |
| 加载态 | 首屏构建 / 主题初次应用 | 轻量骨架屏或占位色块，避免白屏闪烁；本期数据为本地同步，加载态主要体现在首帧渲染前 |
| 空态 | 搜索无命中、曲目集合为空 | 居中图标 + 简明文案（如「没有找到相关歌曲」），不展示空白区域 |
| 错误态 | 资源加载失败 / 运行时异常 | 友好提示 + 重试入口（若可恢复）；错误信息不暴露技术细节给用户，控制台保留完整日志 |
| 禁用态 | 未播放时迷你条播放按钮 | 降低透明度，禁止点击 |
| 反馈 | 收藏、模式切换、主题切换 | 图标 / 配色即时变化，配合轻微动效确认操作生效 |

### 6.6 可访问性

- 所有可点击区域（按钮、曲目行、歌词行）触控尺寸不小于 44×44px；
- 图标按钮配有 `aria-label`，状态按钮使用 `aria-pressed`；
- 进度条使用语义化 slider 角色，支持键盘方向键调节；
- 选中态、高亮态不单纯依赖颜色区分，辅以图标或字重；
- 文本与背景对比度满足基础可读要求。

### 6.7 文案规范

- 文案简洁、口语一致，避免技术术语出现在面向用户的界面；
- 空状态如实说明并给出下一步操作（如「还没有音乐，导入本地文件开始听」）；
- 涉及删除 / 清除的文案须说明影响范围与「不影响设备原文件」。

## 8. 非功能需求与约束

### 8.1 技术约束

- 界面层使用 React + TypeScript，样式使用 Tailwind CSS，组件采用 shadcn 风格（源码复制进项目，自行维护）；
- 本期运行环境为浏览器，无后端服务、无数据库、无账号体系；
- 构建工具为 Vite，产物为纯静态文件（HTML + JS + CSS），可托管于 GitHub Pages；
- 架构分层保持单向依赖，核心逻辑与平台适配分离，为阶段二 / 三 Tauri 化预留替换点；
- 依赖按需引入，不重复引入功能相似的库。

### 8.2 数据持久化边界

- 音频本体、元数据、封面与歌词存 IndexedDB；收藏、历史、主题、歌单存 localStorage；均在本机浏览器内，刷新 / 重开后自动恢复；
- 播放进度与队列为会话态，刷新后不保留（已知取舍）；
- 清除浏览器站点数据会一并清除已导入音频，设置页文案已提示。

### 8.3 性能要求

- 首屏在手机浏览器可完成渲染，不出现长时间白屏；
- 曲目量为用户真实曲库规模（通常数十至数百首），列表不做虚拟化（已知取舍，超大曲库时再评估）；
- 进度由音频 `timeupdate` 事件驱动；
- 玻璃效果依赖 `backdrop-filter`，歌词页等高频滚动区避免叠加多层模糊；不支持或系统要求减少透明度时降级实底；
- 动画优先使用 `transform` / `opacity`（合成器路径），避免触发布局重算；
- 关注生产构建包体积：标签解析库按需动态加载，不进首屏主包。

### 8.4 兼容性

- 目标：现代移动端浏览器（Safari / Chrome 近两年版本）与桌面主流浏览器；
- `file://` 协议下部分资源加载可能受限，须经 HTTP(S) 访问。

### 8.5 安全与隐私

- 不采集用户数据，不发起拉取个人信息的网络请求；
- 代码中不得硬编码密钥、令牌等敏感信息；
- 产品不内置任何音频与歌词内容；用户导入文件的版权由用户自行负责，产品只做本机播放与整理；
- 阶段二（App 达到上架级质量）前需补齐隐私政策、权限声明等合规材料。

### 8.6 许可合规

- 优先采用 MIT / Apache-2.0 / ISC 等宽松许可的依赖，确保可商用、可闭源；
- 打包发布时附第三方依赖许可清单；
- 规避 GPL / AGPL 许可的代码直接进入产品（尤其是借鉴开源播放器实现时，只学设计不复制源码）；
- 不接入任何聚合音源或规避版权限制的功能。

## 10. 后续阶段目标（非本期交付）

> 以下阶段仅定义目标、前置条件与风险，不展开逐功能需求。进入对应阶段前，须单独做需求细化与可行性验证。

### 10.1 阶段二：手机 App（上架级质量标准）

- **目标**：以 Tauri Mobile 构建 iOS / Android 应用，界面复用 React 组件，Rust 核心接入真实本地音频与系统能力，达到上架级质量标准（不实际提交应用商店）。
- **前置决策**：音频来源与曲库版权、目标商店、开发者账号、签名与证书、隐私政策。
- **主要风险**：见 §10.3。

### 10.2 阶段三：Windows 桌面版

- **目标**：以 Tauri Desktop 将同一套 React 界面与 Rust 核心构建为 Windows 原生桌面程序，接入真实本地音频播放。
- **前置决策**：音频来源（本地文件导入 / 内置授权资源）、文件系统访问范围。
- **主要风险**：系统 WebView 版本差异、原生能力覆盖、打包体积与签名。

### 10.3 后续阶段关键风险（如实记录）

| 风险 | 说明 | 影响 |
| --- | --- | --- |
| 移动端成熟度 | 截至 2026 年，Tauri Mobile 虽已可用，但官方与实测均提示：适合「桌面为主、手机为伴」的工具型 App，复杂手势 / 深度原生 UI / 后台任务仍需原生代码；上架级标准的达成存在不确定性 | 手机端体验与达标周期存在变数 |
| 原生体验 | 触控手感、长列表、高频动画、系统转场一致性需额外打磨 | 体验可能不及纯原生方案 |
| 上架级合规要求 | 签名、权限声明、崩溃排查、包体控制、审核规范、隐私政策 | 达标周期与变数大 |
| 渲染一致性 | 桌面 / 移动使用各平台系统 WebView，渲染行为不完全一致 | 不能假设三端像素级一致 |
| 曲库版权 | 真实音乐涉及版权授权 | 未解决前无法达到上架级质量标准 |

> 结论：阶段二、阶段三均不在本期承诺。本期只验证网页端，并把架构扩展点留好，降低后续改动成本。
